# BOOST (שם זמני) — קוד קופון אחד, כולם מרוויחים

פלטפורמת שיווק מבוסס-ביצועים לעסקים חדשים: העסק לא משלם שקל מראש — רק כשמכירה
קרתה בפועל דרך קוד קופון של משפיען. כל אחד יכול להירשם כמשפיען, לקבל קוד אישי
ולהרוויח עמלה אמיתית מכל קנייה.

## מודל הכסף

העסק מגדיר לכל קמפיין **תקציב הטבה קבוע** מכל מכירה, למשל 20%:

| חלק            | דוגמה | מקבל     |
| -------------- | ----- | -------- |
| הנחה לקונה     | 10%   | הקונה    |
| עמלת משפיען    | 7%    | המשפיען  |
| דמי פלטפורמה   | 3%    | אנחנו    |

**עקרון המפתח:** מדרגות המשפיענים (ברונזה / כסף +1% / זהב +2%, לפי מכירות
חודשיות) ממומנות **מדמי הפלטפורמה, לא מהעסק**. העלות לעסק קבועה וידועה מראש
תמיד — ולנו משתלם לוותר על חלק מהעמלה כי נפח המכירות גדל.

## הגנות מובנות (נקודות עיוורות שכבר טופלו בקוד)

- **קנייה עצמית** — משפיען לא יכול לממש את הקוד של עצמו (`SELF_REDEMPTION`).
- **קניבליזציה** — ברירת מחדל: קופון ללקוחות חדשים של העסק בלבד (`NOT_NEW_CUSTOMER`).
- **תקרת תקציב** — תקרת מימושים חודשית אופציונלית לקמפיין (`MONTHLY_CAP_REACHED`).
- **דיווח אמין** — מימוש נרשם רק דרך ה-API עם מפתח סודי של העסק (`BAD_SECRET`),
  לא בדיווח ידני של העסק.
- **חיוב כפול** — החנות שולחת `order_id`; שליחה חוזרת של אותה הזמנה מחזירה את
  הרישום הקיים ולא משלמת עמלה שנייה. נאכף גם באינדקס ייחודי בבסיס הנתונים.
- **החזרות** — עמלה מוחזקת 14 ימים (חלון הביטול בעסקת מכר מרחוק) לפני שהיא זמינה
  למשיכה. הזמנה שבוטלה מבטלת את העמלה ויורדת מהסטטיסטיקות של שני הצדדים.

## החלטות מוצר (01.09.2026)

1. משפיען מרוויח **עמלה כספית** לכל מכירה (לא רק הנחות אישיות).
2. מתחילים מ**חנויות אונליין** (אינטגרציית קופה דרך API); עסקים פיזיים בהמשך.
3. פיילוט עם עסק ראשון אמיתי אחד.
4. קידום בתשלום לעסקים — לא בשלב הזה.

## ארכיטקטורה

```
web/                    Next.js 15 (App Router, RTL עברית)
  lib/domain/           הלוגיקה העסקית הטהורה — חלוקות, מדרגות, ולידציות
  lib/store/            ממשק DataStore + מימוש in-memory עם נתוני דמו
  app/                  דפים: נחיתה, כניסה, דשבורדים, קמפיינים, סימולטור
  app/api/redeem/       ה-endpoint שחנות של עסק תקרא לו בקופה
  tests/                בדיקות vitest מלאות ללוגיקה ולזרימות
db/migrations/          סכמת Postgres מלאה + RLS + RPCs, מוכנה ל-Supabase
```

**שני מצבי הפעלה.** בלי משתני הסביבה של Supabase האפליקציה רצה על נתוני דמו
בזיכרון, עם כניסה ללא סיסמה וסימולטור פתוח — נוח לפיתוח, לא מיועד לנתונים
אמיתיים. עם `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` ו-`SUPABASE_SECRET_KEY`
היא עוברת לבסיס הנתונים האמיתי, ושתי הדלתות האלה **נסגרות אוטומטית**:
ההתחברות עוברת ל-Supabase Auth (אימייל וסיסמה) והסימולטור דורש עסק מחובר
שבודק רק את הקודים של עצמו. `DEMO_MODE` יכול לכפות כל אחד מהמצבים.

## הרצה מקומית

```bash
cd web
npm install
npm test        # בדיקות הלוגיקה והזרימות
npm run dev     # http://localhost:3000
```

משתמשי דמו: דנה (עסק), נועה ועומר (משפיענים) — כניסה בלחיצה מדף ה-login.

## צעדים הבאים (לפי סדר)

תוכנית העבודה המלאה: `docs/` וטיוטות משפטיות ב-`docs/legal/`.

1. **חיבור בסיס הנתונים לאתר החי** — הסכמה והנתונים כבר קיימים ב-Supabase; חסרים
   משתני הסביבה `SUPABASE_URL` ו-`SUPABASE_SECRET_KEY` בסביבת האירוח.
2. **גיבוב מזהה הקונה** — המזהה משמש להשוואת שוויון בלבד, ולכן אפשר לאחסן אותו
   מגובב במקום גלוי ולהפסיק להחזיק אימיילים של צדדים שלישיים (ראו `docs/legal/privacy.md`).
3. אינטגרציה ראשונה אמיתית לפי פלטפורמת החנות של העסק הראשון.
4. הגבלת קצב על `/api/redeem` (דורשת מונה משותף — אחרי חיבור בסיס הנתונים).
5. חלון זמן ותיעוד לביטול עמלה: `cancelled_at`, סיבה, והתראה למשפיען.
6. לינק מעקב למשפיען (קליקים, לא רק קניות).
7. תשלומים בפועל: גבייה מהעסק ותשלום למשפיענים מעל סף, כולל צד מס.
